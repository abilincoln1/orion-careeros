# CareerOS API Reference

Full interactive documentation is auto-generated by FastAPI and served at:

- Swagger UI: `http://localhost:8000/docs`
- ReDoc: `http://localhost:8000/redoc`
- Raw OpenAPI schema: `http://localhost:8000/openapi.json`

This document summarizes the full surface; treat `/docs` as the
canonical, always-current reference once the stack is running.

All endpoints are namespaced under `API_V1_PREFIX` (default `/api/v1`).

## Health

| Method | Path              | Auth | Purpose                                   |
|--------|-------------------|------|--------------------------------------------|
| GET    | `/health`         | none | Human-friendly service summary            |
| GET    | `/health/live`    | none | Liveness probe (process is up)            |
| GET    | `/health/ready`   | none | Readiness probe (checks DB connectivity)  |

`/health/ready` returns HTTP 503 with `{"status": "not_ready", ...}` if the
database is unreachable.

## Auth

| Method | Path                | Auth           | Purpose                              |
|--------|---------------------|-----------------|---------------------------------------|
| POST   | `/auth/register`    | none            | Create a new user account             |
| POST   | `/auth/login`       | none            | Exchange email+password for tokens    |
| POST   | `/auth/refresh`     | none (token)    | Exchange a refresh token for new pair |
| GET    | `/auth/me`          | Bearer access   | Return the authenticated user         |

### `POST /auth/register`
Request:
```json
{ "email": "abi@example.com", "password": "supersecret1", "full_name": "Abiodun Adeniran" }
```
Response `201`:
```json
{ "id": "...", "email": "abi@example.com", "full_name": "Abiodun Adeniran",
  "is_active": true, "is_superuser": false, "created_at": "..." }
```
`409` if the email is already registered.

### `POST /auth/login`
Request:
```json
{ "email": "abi@example.com", "password": "supersecret1" }
```
Response `200`:
```json
{ "access_token": "...", "refresh_token": "...", "token_type": "bearer" }
```
`401` on bad credentials, `403` if the user is inactive.

### `POST /auth/refresh?refresh_token=...`
Response `200`: new `access_token` + `refresh_token` pair. `401` if the
refresh token is invalid, expired, or not of type `refresh`.

### `GET /auth/me`
Header: `Authorization: Bearer <access_token>`
Response `200`: the current user (same shape as register). `401` if the
token is missing/invalid/expired, or the user is inactive.

## Career DNA

All Career DNA endpoints require `Authorization: Bearer <access_token>`
unless noted otherwise, and every endpoint except skill taxonomy search
resolves the acting `Person` from the authenticated token via
`get_current_person` -- there is no code path that accepts another
person's id as a parameter. See `docs/adr/0004-career-dna-domain-model.md`
for the full domain model and design rationale.

List endpoints return a paginated envelope:
```json
{ "items": [...], "total": 0, "offset": 0, "limit": 50 }
```
`offset` defaults to 0, `limit` defaults to 50 (max 200).

### Person / CareerProfile

| Method | Path                              | Purpose |
|--------|-----------------------------------|---------|
| POST   | `/career-dna/person`              | Bootstrap the caller's Career DNA profile (one-time; `409` if it already exists) |
| GET    | `/career-dna/person/me`           | Get the caller's Person record (`404` if not yet created) |
| PATCH  | `/career-dna/person/me`           | Partial update (only fields sent are changed) |
| GET    | `/career-dna/person/me/profile`   | Get the caller's CareerProfile (created automatically alongside Person) |
| PATCH  | `/career-dna/person/me/profile`   | Partial update of the CareerProfile |

`PersonCreate`/`PersonUpdate`: `first_name`, `last_name` (1-100 chars),
`preferred_name`, `headline` (optional, max 100/255 chars). Person is not
auto-created at registration -- see the module docstring in
`app/services/person_service.py` for why.

### Employment

| Method | Path                                          | Purpose |
|--------|-----------------------------------------------|---------|
| POST   | `/career-dna/employments`                     | Create an employment record |
| GET    | `/career-dna/employments`                     | List (filterable by `is_current`) |
| GET    | `/career-dna/employments/{id}`                | Get one |
| PATCH  | `/career-dna/employments/{id}`                | Corrections only (dates, description, is_current) -- **not** role/title |
| POST   | `/career-dna/employments/{id}/promote`        | Record a promotion: creates a new chained row, closes this one out |
| DELETE | `/career-dna/employments/{id}`                | Delete |

`EmploymentCreate` requires `employer_name`, `role_title`,
`employment_type`, `start_date`; `end_date` must not be before
`start_date` (`422` otherwise). At most one *primary* (full-time/
part-time) current employment is allowed per person, enforced at the
database level -- a second one returns `409`.

**Note:** the read schema (`EmploymentRead`) returns the role field as
`role_title_raw`, not `role_title` -- `role_title` is only the
`EmploymentCreate` input field name. This is intentional, not a bug (the
raw string is stored as-is pending future normalization against a
`Role` taxonomy), but is easy to miss if you assume symmetric field
names between create and read.

Role/title changes must go through `POST /{id}/promote`
(`EmploymentPromote`: `new_role_title`, `effective_date`,
optional `employment_type`) -- `PATCH` cannot edit the title, by design.
See ADR 0004 Decision 3.

### Skill

| Method | Path                                      | Auth | Purpose |
|--------|--------------------------------------------|------|---------|
| GET    | `/career-dna/skills`                       | none | Search the shared skill taxonomy (`?q=` substring match) |
| POST   | `/career-dna/person-skills`                | required | Add a skill to the caller's profile |
| GET    | `/career-dna/person-skills`                | required | List the caller's skills (filterable by `skill_type`) |
| PATCH  | `/career-dna/person-skills/{id}`           | required | Update proficiency/years/etc. |
| DELETE | `/career-dna/person-skills/{id}`           | required | Remove; also cleans up any dependent EvidenceLinks |

`PersonSkillCreate` requires `skill_name`, `skill_type`, `proficiency`;
`years_experience` is optional (0-99.9). The underlying `Skill` taxonomy
is deduplicated by normalized name at the database level -- two people
adding "Python" and "python" resolve to the same taxonomy row.
`attribution_source` is never a client-settable field on this schema --
see Evidence below.

### Evidence

| Method | Path                                              | Purpose |
|--------|----------------------------------------------------|---------|
| POST   | `/career-dna/evidence`                             | Create a piece of evidence |
| GET    | `/career-dna/evidence`                             | List the caller's evidence |
| POST   | `/career-dna/evidence/{id}/link`                   | Attach evidence to a subject (PersonSkill, PersonCompetency, PersonTechnology, Certification, Education, Project, Achievement, Publication, or Reference) |
| DELETE | `/career-dna/evidence/{id}/link/{link_id}`         | Remove a link |
| DELETE | `/career-dna/evidence/{id}`                        | Delete evidence (cascades its links) |

`EvidenceCreate` requires `evidence_type`, `title` (1-255 chars);
`description` and `source_url` (max 500 chars) are optional.

**Core guarantee:** for the three attribution-bearing subject types
(PersonSkill, PersonCompetency, PersonTechnology), linking qualifying
evidence is the *only* way `attribution_source` becomes `verified` --
there is no endpoint or field that sets it directly. Removing the last
link demotes it back to `inferred` (never back to `self_reported`).
Deleting the Evidence itself cascades the same recompute. See ADR 0004
Decision 6 and `docs/SPRINT-2-ARCHITECTURE-REVIEW.md` must-fix #5.

## Error format

All handled errors return:
```json
{ "error": { "code": 404, "message": "..." } }
```
Validation errors (`422`) additionally include `details` with field-level
Pydantic error info.

## Versioning

Every endpoint is under `/api/v1`. Breaking changes in future sprints
introduce `/api/v2` rather than mutating existing contracts, per the "API
First" principle.
