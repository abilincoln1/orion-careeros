# Technical Debt Register

Living document. Every item here is either fixed (moved to "Resolved") or
still open. Nothing here should exist only in conversation or memory --
if it's known, it's written down.

## Open

| ID | Category | Description | Impact | Remediation | Priority |
|---|---|---|---|---|---|
| TD-001 | Dependency risk | `orion_kernel` currently has exactly one consumer (CareerOS backend). Its function signatures were designed correctly for that one case but are unvalidated against a second product's needs. | Low today; the first real second product may require breaking changes to kernel interfaces. | Do not over-generalize speculatively (see `governance/ARCHITECTURE_PRINCIPLES.md` #7); revisit kernel API surface when the second product is actually authorized. | Low |
| TD-002 | Security | No role-based authorization anywhere on the platform. Auth framework establishes identity only. | Blocks any multi-user or multi-tenant phase; also blocks Audit (kernel responsibility) which depends on knowing what a user was allowed to do. | Implement Authorization as a Platform Kernel capability (see `docs/platform/PLATFORM_KERNEL.md`) when a sprint authorizes multi-user work. | Medium (not urgent for single-user Sprint 1/1-Closure scope) |
| TD-003 | Security | No rate limiting or account lockout on `/auth/login` or `/auth/register`. | Acceptable for local single-user use; a real risk if ever exposed beyond localhost. | Add rate limiting (e.g. `slowapi` or a reverse-proxy-level limit) before any externally-reachable deployment. | Medium |
| TD-004 | Security | No dependency/CVE scanning configured (e.g. `pip-audit`, `npm audit` is available ad hoc but not gated in CI because no CI exists yet -- see TD-006). | Unknown vulnerable dependencies could go unnoticed. | Add `pip-audit` and `npm audit --audit-level=high` as CI steps once CI exists. | Medium |
| TD-005 | Configuration | Default `SECRET_KEY` in `.env.example` is an intentionally insecure placeholder. | Would be a real vulnerability if deployed unchanged. | Documented in README and `.env.example`; enforce via a startup check that refuses to boot with the placeholder value when `ENVIRONMENT=production`. | Medium |
| TD-006 | Process | No CI pipeline exists. All verification in this session was run manually (pytest, tsc, embedded-Postgres smoke test). | Verification is not automatically re-run on every change; regressions could be reintroduced silently. | Add a minimal CI workflow (pytest + tsc -b) -- recommended as the first Sprint 2 prerequisite in `docs/SPRINT-2-IMPLEMENTATION-PLAN.md`. | High |
| TD-008 | Metrics | No historical trend for any metric in `docs/METRICS.md` -- only a single baseline snapshot exists. | Cannot yet detect metric regression over time (e.g. complexity creeping up). | Re-run `scripts/metrics/collect_metrics.py` at the end of every sprint and append to a tracked history file. | Low |
| TD-009 | Frontend | Frontend has no test suite (only `tsc -b` type-checking and a production build were verified). | UI regressions would not be caught automatically. | Add a minimal component test (e.g. Vitest + React Testing Library) once the frontend has more than a health-check shell to test. | Low |
| TD-010 | Domain config | `config/config.example.yaml` documents the intended shape of domain configuration (salary bands, commute radius, matching weights, watchlists, learning priorities) but nothing in the codebase reads it. | None yet -- correct for current scope -- but risk of being mistaken for already wired up. | Implement when the Matching Engine sprint is authorized; until then, leave the flag in `docs/platform/PLATFORM_KERNEL.md` and here as the single source of truth on its status. | Low |
| TD-011 | Security (found via metrics framework) | `pip-audit` run as part of `scripts/metrics/collect_metrics.py` found 22 known vulnerabilities across pinned dependencies: `python-jose 3.3.0` (5, including algorithm-confusion-class issues), `python-multipart 0.0.20` (6), `starlette 0.41.3` (9, pulled in by `fastapi==0.115.6`), `pytest 8.3.4` (1), `ecdsa 0.19.2` (1, transitive via python-jose). | `python-jose` in particular is a known-risky, thinly-maintained JWT library; CareerOS's entire auth framework depends on it. | Evaluate replacing `python-jose` with `PyJWT` (actively maintained, does not share the same CVE history) as a dedicated security task -- not done in this session because a crypto-library swap is a code change with test-coverage implications, not a "safe improvement" to make casually alongside a documentation-heavy sprint. Bump `starlette`/`fastapi`, `python-multipart`, and `pytest` to their latest patched versions in the same pass. | High |
| TD-012 | Architecture (found via Docker Build Review / Sprint 2 Readiness directive) | `orion_kernel` is installed by CareerOS via a repo-relative editable path (`-e ../../../platform/kernel`), which only works because the kernel and its one consumer live in the same repository. A genuinely separate repository (e.g. NDIP) cannot reach across an independent git checkout via a relative path, so the kernel cannot be consumed cross-repository today. See `docs/adr/0003-docker-naming-and-multi-project-isolation.md` Decision 2. | Blocks nothing today (CareerOS is still the only ORION product); would block a second product in its own repository from adopting the kernel until fixed. | When a second product actually needs the kernel: tag a kernel release in this repo and have the new product install it via `pip install git+https://.../orion-kernel.git@<tag>` instead of a relative path (or extract `platform/kernel` to its own repository at that point). Not implemented now, per explicit directive not to build cross-repository sharing yet. | Medium (zero urgency today; blocking the moment a second product is authorized) |

| TD-R06 | Bug (found via live Docker run) | `docker compose up --build`, run by the user on their actual Windows/Docker Desktop machine, crash-looped `careeros_backend` with `pydantic_settings.sources.SettingsError` / `JSONDecodeError` on `CORS_ORIGINS`. Root cause: pydantic-settings treats `List[str]` fields as "complex" and tries to JSON-decode the raw environment variable *before* any pydantic validator runs, so a plain comma-separated value (`.env.example`'s actual format) crashed at the settings-source level, never reaching the existing `_split_cors` before-validator. This session's Docker-less verification (embedded Postgres, direct env var assignment in Python) never set `CORS_ORIGINS` from an env string the way `docker compose --env-file .env` does, so it did not catch this. | Added `NoDecode` annotation (`pydantic_settings.NoDecode`) to `CORS_ORIGINS` in `platform/kernel/orion_kernel/config.py`, which tells pydantic-settings to leave the raw string alone for the existing validator to split. Reproduced the exact crash and confirmed the fix locally (Python, no Docker needed, since the bug is in pydantic-settings' env-parsing, not Docker itself) before reporting fixed; full backend test suite (12/12) re-run and still passing. **Confirmed inside an actual container**: the user re-ran `docker compose up --build` and the backend started cleanly with no crash loop -- see TD-R07. |
| TD-R07 | Verification gap (was TD-007) | `docker compose up --build` had never been executed end-to-end to completion; the equivalent verification (embedded PostgreSQL, live `uvicorn` process, direct HTTP calls) proved the application + database integration but not the container build, inter-container networking, or Docker's own `HEALTHCHECK` directive. | User ran `docker compose up --build` a second time after the TD-R06 fix. Result: backend started cleanly (no crash loop), migrations applied, frontend served on `:5173`, and the log showed recurring successful `GET /api/v1/health` requests at ~30s intervals -- Docker's `HEALTHCHECK` directive itself firing and passing, which no Docker-less verification could have exercised. Full end-to-end Docker verification is now complete; `docs/RiskRegister.md` RT-01 and `docs/SPRINT-1-ACCEPTANCE-REPORT.md` updated accordingly. |
